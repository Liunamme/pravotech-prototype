# ПравоТех — прототип агентной платформы для юристов

[![CI](https://github.com/Liunamme/pravotech-prototype/actions/workflows/ci.yml/badge.svg)](https://github.com/Liunamme/pravotech-prototype/actions/workflows/ci.yml)
[![Deploy](https://github.com/Liunamme/pravotech-prototype/actions/workflows/deploy.yml/badge.svg)](https://github.com/Liunamme/pravotech-prototype/actions/workflows/deploy.yml)

**Живая демонстрация: https://liunamme.github.io/pravotech-prototype/**

Рабочий прототип B2B-платформы, в которой AI-агент выполняет работу юриста: ведёт дело,
работает с документами и сроками, предлагает действия — а юрист подтверждает, изменяет
или отклоняет. Один и тот же агент присутствует во всех частях продукта.

Прототип отвечает на тестовое задание (`tech-task.md`). Агент замокан заготовленными
сценариями, но интерфейс живой: стриминг ответа по токенам, честные статусы длинных
операций с прогрессом, уход тяжёлых задач в фон, кликабельные источники у каждого
утверждения агента.

## Что это и чего здесь нет

Это **прототип**, а не продукт. Он сделан, чтобы показать работающую идею и
взаимодействие, и намеренно не имеет продуктовой обвязки:

- **агент замокан** — сценарии в `src/core/agent`, никаких обращений к LLM или внешним
  сервисам; сеть из браузера не используется вовсе;
- **нет входа и разграничения доступа** — открывший ссылку видит всё;
- **ничего не сохраняется** — состояние живёт в памяти вкладки, перезагрузка страницы
  начинает демонстрацию с чистого листа (это выбор, а не недоделка: показ должен быть
  предсказуемым);
- **проверка форм — только ради интерфейса.** Она не даёт отправить пустое уведомление
  или платёж на ноль и объясняет, что не так, но защитой не является: те же правила
  обязаны повториться на сервере (см. «Что обязательно добавить к продукту»);
- **адаптив сделан на всех трёх ширинах** — десктоп (≥1280), планшет (768–1279, очередь в
  выдвижной панели) и телефон (<768, нижние вкладки и по одной поверхности за раз).

## Запуск

Нужен **Node 22** (зафиксирован в `engines`, та же версия в CI).

```bash
npm install
npm run dev      # http://localhost:5173
```

Прод-сборка и локальный предпросмотр:

```bash
npm run build    # tsc -b && vite build → dist/
npm run preview
```

Проверки — те же, что гоняет CI:

```bash
npm run lint     # oxlint
npm test         # vitest run — юнит-тесты логики
npm run dry-run  # прогон всех сценариев мок-агента в консоль (без UI)
npm audit --omit=dev --audit-level=high
```

`npm run test:watch` — тесты в режиме наблюдения во время работы.

## С чего начать осмотр

1. **`/#/today` — уровень 1 «Сегодня».** При входе агент стримит утренний дайджест со
   ссылками на источники; справа — очередь карточек действий со всех пространств и сроки.
2. Кликните по источнику в сообщении (напр. «п. 7.3») — **документ открывается справа
   в нужном месте**, чат остаётся виден.
3. Разберите карточку в очереди: **Подтвердить / Изменить / Отклонить**. «Изменить»
   раскрывает форму на месте с подсветкой правок; после решения — тост с «Отменить».
4. Спросите **«какие договоры продлятся автоматически»** — увидите честный прогресс
   «Читаю договоры · 7 из 12».
5. Спросите **«подготовь позицию по делу А40»** — тяжёлая операция уходит в фоновый
   лоток, интерфейс не заперт, по завершении приходит уведомление.
6. Перейдите в пространство в левой рейке — **та же грамматика на уровне 2**: список
   чатов-задач, вкладки контекста, очередь карточек этого пространства.

Проверьте на прочность: кнопка **«Остановить»** во время стриминга, запрос про
**«выписку из ЕГРЮЛ»** (честная ошибка внешнего сервиса с «Повторить»), слово
**«расторжение»** (уточняющий вопрос агента), переключатель темы внизу рейки.

## Архитектурные решения

Подробности — в `docs/`. Коротко о главном:

**Платформа, а не экран.** Ядро (`src/core`) не знает о конкретных пространствах.
Новое рабочее пространство = один манифест (`WorkspaceManifest`) + сид-данные, без правок
в ядре и без изменения раскладки. В прототипе два разнотипных пространства —
«Обязательства по договорам» и «Судебные дела» — с разными типами карточек, вкладок
контекста и навыков агента, но одной оболочкой. Это доказательство переиспользуемости.

**Транспорт агента подменяем.** UI работает с интерфейсом `AgentTransport`, отдающим
поток событий (`token`/`status`/`citation`/`card`/`handoff`/`error`/…). Мок реализует
этот интерфейс; замена на реальный SSE-транспорт — одна строка в провайдере, компоненты
не меняются.

**Одна карточка — один рендерер.** Карточка действия в очереди «Сегодня» и в своём
пространстве — одна запись стора, отрисованная одним `CardRenderer`. Решение по карточке
в одном месте немедленно видно в другом.

**Честная латентность.** Три класса ожидания: <300 мс — без индикатора; 0.3–3 с —
статус в потоке чата; >3 с — операция уезжает в фоновый лоток, юрист свободен.
Бесконечного спиннера без подписи в интерфейсе нет.

**Кликабельные источники.** Каждое утверждение агента несёт ссылку на конкретный пункт
документа. Ссылка открывает документ в нужном месте и шарится через URL
(`?doc=..&anchor=..`). Целостность ссылок проверяется dev-ассертами при загрузке —
битая ссылка падает громко, а не молча. Ссылка на удалённый документ или чужой диалог
не подменяет смысл молча: приложение говорит, что не так, и убирает ложное обещание
из адреса.

**Сроки и очередь — вкладками, а не двумя блоками подряд.** Исходная схема
предполагала календарь вторым блоком под очередью; в `TodayPage/RightPanel.tsx` это
переключатель «Очередь · Сроки». Причина: оба списка длинные и конкурируют за одну и ту
же вертикаль, а блок «Ближайшее» при этом остаётся виден всегда. Решение осознанное —
не «возвращать как было» при последующих правках.

**Решение по карточке принимается один раз.** У карточки есть машина состояний:
решение — только из «не решено», исполнение — только из принятого решения, повтор —
только из сбоя. Двойной клик, вторая вкладка и запоздавший ответ исполнения не создают
второго действия. Клиентская половина контракта; серверную см. ниже.

**Сроки не пересчитываются в часовой пояс читателя.** Срок в карточке — юридический
факт в своём смещении (`+03:00`), поэтому правка даты меняет только календарный день,
не трогая время и смещение. Проверено тестами под четырьмя поясами, включая переход на
летнее время.

## Стек

Vite · React 19 · TypeScript (strict) · React Router 8 (HashRouter) · Zustand ·
CSS Modules · Radix UI (headless-примитивы) · lucide-react · date-fns. Тесты — Vitest.

React и роутер подняты с 18/7 в ходе предрелизного аудита: в 7.x был high-CVE
(GHSA-qwww-vcr4-c8h2), а единственная исправленная версия роутера требует React ≥ 19.2.7.
В восьмой ветке пакета `react-router-dom` больше нет — импорт идёт из `react-router`.

Дизайн-система — собственная, на семантических CSS-переменных (`src/shared/styles/tokens.css`),
светлая и тёмная темы. UI-примитивы построены на headless-примитивах Radix (готовая
доступность) со своей стилизацией — без UI-китов, чтобы сохранить полный контроль над
плотностью и поведением. Адаптив двухуровневый: медиа-запросы решают судьбу колонок,
контейнерные запросы (`@container`) — внутреннюю раскладку компонентов, потому что ширины
панелей задаёт пользователь ресайзом.

## Структура

```
src/
  app/          роутер, провайдеры, тема
  shared/       ui/ (примитивы) · lib/ (утилиты, даты) · styles/ (токены, reset)
  core/         layout · chat · cards · calendar · documents · tasks · agent
  workspaces/   registry + obligations/ + litigation/ (манифесты пространств)
  store/        Zustand-слайсы, селекторы, dev-ассерты целостности
  pages/        TodayPage · WorkspacePage · SettingsPage
  types/        доменная модель
docs/           SPEC · DOMAIN · SCENARIOS · UX — контракты проекта
docker/         конфигурация nginx для образа (Pages его не использует)
.github/        workflows: ci.yml (проверки) · deploy.yml (Pages) · dependabot.yml
```

Тесты лежат рядом с проверяемым кодом (`*.test.ts`) и вынесены в отдельный проект
TypeScript (`tsconfig.test.json`) — приложению типы Node не нужны, а тестам нужен
`process` для переключения часового пояса.

## Тесты

`npm test` — Vitest, среда node. Покрыта логика, где ошибка тихая и дорогая: правка
сроков в разных часовых поясах, проверка форм карточек, машина состояний решения,
порядок очереди, разбор сбоев транспорта, темы диалогов, идентификаторы.

Рендер компонентов и сквозные сценарии тестами не покрыты сознательно: раскладка сейчас
меняется (впереди планшет и мобильная версия), и такие тесты пришлось бы переписывать
вместе с ней. До тех пор интерфейс проверяется вручную и скриптами Playwright.

## CI/CD

`.github/workflows/ci.yml` — линт (предупреждения считаются ошибками), типы, тесты,
сухой прогон агента, сборка, аудит production-зависимостей. Гоняется на каждый pull
request.

`.github/workflows/deploy.yml` вызывает те же проверки и публикует на GitHub Pages
только после зелёного результата. Включить публикацию один раз:
**Settings → Pages → Source → «GitHub Actions»**.

Чтобы мимо проверок нельзя было протолкнуть прямой push, включите защиту ветки:
**Settings → Branches → правило для `main`** → «Require a pull request before merging» и
«Require status checks to pass» (отметить проверку `Проверки`). Из кода это не
включается — только настройками репозитория.

Обновления зависимостей ведёт Dependabot (`.github/dependabot.yml`): npm еженедельно
мелкие обновления одной группой, сами actions — раз в месяц.

Сборка использует относительные пути (`base: './'`) и hash-роутинг, поэтому работает
на любом хостинге и в подпапке без правки конфигурации.

**Адрес опубликованного прототипа:** https://liunamme.github.io/pravotech-prototype/

### Контейнер

`Dockerfile` для GitHub Pages не нужен и не используется — он на будущее (свой хостинг,
домен, показ одной командой):

```bash
docker build -t pravotech .
docker run --rm -p 8080:8080 pravotech
```

Две стадии, раздача через `nginx-unprivileged` (работает не от root), заголовки
безопасности в `docker/nginx.conf` — CSP, `X-Content-Type-Options`, `Referrer-Policy` и
прочее, чего GitHub Pages настроить не даёт. Образ в этой среде не собирался: Docker
недоступен, проверена только сборка из урезанного `.dockerignore` контекста.

## Про линт

`design/**` (выгрузка макета) и `dist/**` из проверки исключены — это не наш код.

Правило `react/only-export-components` точечно отключено в `.oxlintrc.json` для
`workspaces/**/cards/*.tsx`, `ThemeProvider` и `Toast`. Причина одна и та же: там
компонент лежит рядом со своим контрактом (`CardTypeDef` объединяет `Body`, `EditForm`,
`validate` и `execute`) или провайдер рядом со своим хуком. Разносить их по файлам —
ломать контракт ради подсказки о fast refresh. Других отключений нет, и в CI любое новое
предупреждение роняет сборку.

## Что обязательно добавить к продукту

Прототип честно доходит до границы, за которой начинается доверенная сторона. Что должно
появиться вместе с реальным API:

- **SSO/OIDC, роли и изоляция арендатора** на каждой операции;
- **проверка на сервере** — те же правила, что в формах, плюс выборка карточки по id,
  сверка роли, состояния и допустимости перехода. Клиенту нельзя верить ни в payload, ни
  в `workspaceId`/`cardId`/`priority`/`sources`;
- **идемпотентность необратимых действий** — ключ идемпотентности и ожидаемая версия
  карточки (optimistic locking); клиентская защита от повторов уже есть, но она только
  клиентская;
- **журнал необратимых действий**: кто, когда, что подтвердил и какую версию текста;
- **лимиты размера, rate limiting, CSRF** там, где появятся cookie;
- **заголовки безопасности** (CSP/HSTS и прочее) — GitHub Pages их не даёт, поэтому для
  настоящего кабинета нужен другой хостинг; заготовка есть в `docker/nginx.conf`;
- **защита от prompt injection на стороне оркестрации**: документы и сообщения — данные,
  а не инструкции; список разрешённых инструментов, подтверждение юристом и проверка
  политики на сервере обязательны.
