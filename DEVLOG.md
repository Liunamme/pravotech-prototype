# DEVLOG — ПравоТех

Журнал разработки прототипа агентной платформы для юристов.
Ведётся по ходу работы, чтобы не терять контекст между сессиями.

**План:** `~/.claude/plans/cozy-dancing-wand.md`
**ТЗ:** `tech-task.md`

**Контракты (читать перед любой работой над кодом):**
- `docs/SPEC.md` — токены, структура файлов, конвенции, критерии готовности
- `docs/DOMAIN.md` — доменная модель, транспорт агента, манифест пространства, стор
- `docs/SCENARIOS.md` — поведение мок-агента, тайминги, канон демо-сущностей
- `docs/UX.md` — интеракционный контракт: анатомия карточки, поведение очереди,
  инспектор, срочность, тексты пустых состояний, хореография движения (этапы 5–7)

**Режим работы:** оркестратор (Opus) производит контракты и решения и проверяет результат;
исполнители (Sonnet) пишут код против контрактов. `DEVLOG.md` ведёт оркестратор —
агенты отдают наблюдения в отчёте, чтобы не конфликтовать за файл.

## Зафиксированные решения

| Решение | Значение | Почему |
|---|---|---|
| Стек | Vite · React 18 · TS strict · React Router · Zustand | Требование ТЗ (React+TS), Zustand — минимум церемоний для прототипа |
| Стилизация | **CSS Modules** (не Tailwind) | Layout-тяжёлое приложение, нужны `@container` от ширины панели, токены как настоящий CSS |

| Язык | Русский | Домен |

### Отступления от схемы ТЗ (согласованы)
1. Документ — инспектор поверх правой колонки, не переход на экран.
2. Правая колонка «Сегодня» — сегменты «Очередь · Сроки» + плашка «Ближайшее».
3. «Изменить» — инлайн-раскрытие с diff, не модалка.
4. Undo вместо confirm по умолчанию; confirm только для `destructive`.
5. Лоток фоновых задач в рейке для операций >3s.

## Ключевые архитектурные инварианты

Нарушение любого из них — баг, а не «мелочь».

1. **Новое пространство = один манифест.** Ядро (`src/core`) не знает про `obligations` и `litigation`. Любой `import` из `core` в сторону конкретного пространства — ошибка проектирования.
2. **Одна карточка — один рендерер.** «Сегодня» и пространство рисуют карточку через общий `CardRenderer`. Копипаста запрещена.
3. **Транспорт агента подменяем.** UI работает с `AgentTransport`; замена мока на SSE — одна строка в провайдере.
4. **Токены — единственный источник цвета и отступа.** Literal-значения в `*.module.css` вне `tokens.css` запрещены.
5. **Ширины панелей задаёт пользователь.** Внутренняя раскладка компонентов — только через `@container`, не через медиа-запросы.
6. **Каждое утверждение агента имеет источник.** Блок текста без `citations` — допустим только для служебных сообщений.

**Решения, принятые самостоятельно (SPEC не детализировал):**
1. **API `ResizablePanels`**: `children` — обычный список React-нод, сопоставляется с `panels` по порядку (индекс к индексу), а не по `id`/ключам. Проще для вызывающего кода и достаточно для текущих сценариев; в деве есть `console.warn` при несовпадении длин.
2. **Кого resize-хендл двигает**, когда он стоит между flex-панелью и фиксированной (или между двумя фиксированными): управляемая панель — левый сосед, если он не flex, иначе правый; знак дельты инвертируется для правого случая, чтобы направление тяги оставалось интуитивным.
3. **Динамический `maxWidth`**: если не передан явно, считается как `containerWidth − ширины резайзеров − минимумы соседей` (для flex-соседа используется внутренняя резервная константа 200px). Так Home/End и ограничение перетаскивания работают без необходимости заранее знать максимум.
4. **Anti-thrashing**: во время `pointermove` ширина пишется напрямую в CSS-переменную (`element.style.setProperty`) через `requestAnimationFrame`-батчинг, без `setState`; в React state (и localStorage) значение коммитится один раз на `pointerup`/`Escape`-эквиваленте. Клавиатурные Arrow/Home/End коммитят сразу (дискретный шаг, не стрим событий).
5. **Значения `-subtle`/`-border`** для `danger/warning/success/info` и `p0–p3` не были зафиксированы в SPEC буквально (только базовый цвет и общее правило для `-fg`). Подобрал их как тонкие тинты/окантовки того же оттенка — по аналогии с уже заданной парой `--color-accent-subtle`/`--color-accent-border`. См. «Открытые вопросы».
6. Страницы (`pages/*`) оформлены как папки-компоненты (`Name.tsx` + `.module.css` + `index.ts`), хотя в дереве файлов SPEC они перечислены плоско — для единообразия с остальными конвенциями кода (п. 4 SPEC, правило 1).
7. Не создавал `workspaces/`, `store/`, `types/domain.ts` — по инструкции этапа 1 это внеobласти («не забегай вперёд»), хотя они и упомянуты в дереве файлов SPEC. Появятся на своих этапах.

**Отложено:**
- Реакция `ResizablePanels` на изменение размеров окна (reflow/reclamp сохранённых ширин при сильном сжатии контейнера) — сейчас ширины не переклэмпливаются при ресайзе окна браузера, что в теории может дать переполнение на очень узких окнах. Для десктоп-прототипа не критично.
- `oxlint`, оставленный дефолтом create-vite-скаффолда, не увязан ни с чем (SPEC линтер не требует); npm-скрипт `lint` есть, но не используется в проверках готовности.

**Грабли:**
- Актуальный `npm create vite@latest -- --template react-ts` по умолчанию ставит React 19 + TypeScript ~6.0 + `oxlint` вместо ESLint и не создаёт непустую директорию — пришлось сгенерировать во временной папке и перенести файлы, а React/`@types/react*` вручную прижать к 18.x под требование SPEC.
- TypeScript 6.0 помечает `baseUrl` в tsconfig как deprecated (TS7 уберёт совсем) — убрал `baseUrl`, `paths` при `moduleResolution: "bundler"` резолвится и без него (проверено `tsc --noEmit` и `vite build`).
- `clsx` типизирован через `export =` — понадобились `esModuleInterop`/`allowSyntheticDefaultImports` в `tsconfig.app.json`, иначе `import clsx, { type ClassValue } from 'clsx'` не собирался.

### Этап 4а — мок агента — 2026-07-24

7 сценариев, транспорт с реальной отменой, dry-run-проверка (`npm run dry-run`).
Проверено оркестратором: `tsc` чист, `any` — 0, импортов React/стора/UI в `core/agent/**` нет
(grep-совпадения оказались комментариями «файл не импортирует React»).

Dry-run подтверждает главное:
- `cancel()` останавливает поток за ~1 мс, `done` не эмитируется — кнопка «Остановить» не будет врать;
- все 33 `SourceRef` сверены с каноном `refs.ts` — расхождений нет, значит на этапе 8
  документы встанут под уже существующие якоря и клик по цитате не приведёт в никуда;
- `tokenize().join('')` побайтово равен исходнику на всех 21 текстах.

Решения исполнителя, которые я принял:
- **Сценарий `failure` с успешным повтором.** Счётчик попыток на тред: первая — ошибка ЕГРЮЛ,
  повтор — успех. Это делает кнопку «Повторить» осмысленной, а не декоративной.
- **`fallback` не заглушка**: узнаёт тему по канону (номер договора, «аренда», «НДА») и отвечает
  предметно с цитатой; если не узнал — честно говорит об этом и предлагает навыки пространства.
- **`tsx` не резолвит value-импорты по алиасу `@/`** (сборка Vite при этом работает). Исполнитель
  убрал единственный такой импорт, приведя модуль к `import type`. Ограничение инструмента,
  не проекта — но знать полезно, если понадобятся ещё скрипты.

Долг: триггер `'цен'` у `priceIncreaseRefusal` совпадёт со словом «оценка». Унаследовано
из моего же `SCENARIOS.md`. На демо не мешает, при желании сузить — на этапе 9.

   прикинут по ширине панели, но `@container` меряет content-box карточки: панель 360 минус

   **Правило записано в `UX.md` §8: пороги контейнерных запросов проверять измерением,
   а не прикидкой по ширине панели.**

Плюс в `UX.md` §2 добавлено правило: `CardTypeDef.Body` **не имеет права дублировать**

## Открытые вопросы

1. Точные hex-значения `-subtle`/`-border` для статусов (`danger/warning/success/info`) и приоритетов (`p0–p3`) не зафиксированы в SPEC (раздел 3) — только базовый цвет и общее правило для `-fg`. Я подобрал тинты/окантовки по аналогии с `--color-accent-subtle/-border`. Нужно ли свериться с дизайнером/утвердить конкретные значения — на будущих этапах, когда появятся бейджи и заметность станет важна визуально?
2. API `ResizablePanels` (форма `children`, семантика того, какая панель «управляется» резайзером между flex- и фикс-соседями) не описана в SPEC детально — задокументировал принятые решения в «Хронике», стоит формально закрепить как часть контракта, если компонент будет переиспользоваться в этапе 7 (инспектор, календарь) с более сложной конфигурацией панелей.

## Долги и упрощения

1. `ResizablePanels` не переклэмпливает сохранённые ширины панелей при сжатии окна браузера — возможен визуальный overflow на очень узких viewport. Отложено как некритичное для десктоп-прототипа.
2. Максимальная ширина панели по умолчанию считается с использованием захардкоженной JS-константы резерва под flex-соседа (200px), не завязанной на токен — осознанное упрощение уровня прототипа.
