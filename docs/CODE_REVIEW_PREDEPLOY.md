# Code review перед публичным деплоем

Дата аудита: 26 июля 2026. Область: весь исходный код `src/`, конфигурация сборки и GitHub Actions, требования из `tech-task.md`, внутренние контракты `docs/`, production-сборка, lint, dry-run мок-агента, `npm audit` и визуальная проверка на desktop (1280 px), tablet (834 px) и mobile (402 px).

## Итоговое решение

Desktop-прототип в целом хорошо реализует главную идею ТЗ: есть два уровня продукта, единая грамматика «чат + действия», два расширяемых пространства, живой мок агента, источники документов и честные состояния длительных операций. Однако **перед публикацией на GitHub Pages следует исправить P0 и P1 ниже**. Особенно важны адаптив и контракты/валидация перед заменой мока на реальный API.

Домен/кастомный домен намеренно не проверялся: это вне текущего этапа.

### Допустимое отступление от исходной схемы

Календарь/сроки в правой колонке сделаны не вторым блоком под очередью, а вкладками «Очередь · Сроки» в `src/pages/TodayPage/RightPanel.tsx`. Это **допустимое и обоснованное** отступление: пользователь переключается между двумя длинными, конкурирующими за вертикальное место списками, а верхний блок «Ближайшее» остаётся видимым всегда. Исходное ТЗ прямо разрешает другой подход при аргументации. Решение нужно сохранить и коротко зафиксировать в README или `docs/UX.md`, чтобы его не «вернули» при последующих правках.

## Что исправить в первую очередь

### P0 — блокирует релиз

#### P0-1. Нет адаптива уровня страницы: интерфейс непригоден на tablet/mobile

**Доказательство.** В `TodayPage.module.css` и `WorkspacePage.module.css` нет breakpoint-логики, которая меняет судьбу колонок. На фактических скриншотах при 834×1194 чат сжат примерно до 150 px, при 402×874 большая часть приложения находится за правой границей. Внутренний контракт `docs/UX.md` требует: 1024–1279 — очередь во выдвижной панели, меньше 1024 — одна колонка с нижними табами «Чат · Очередь · Сроки».

**Исправление.** Реализовать page-level responsive layout в `src/core/layout/**` и страницах:

1. `>= 1440`: текущие три колонки;
2. `1280–1439`: компактный календарь/сроки;
3. `1024–1279`: чат как основная поверхность, очередь доступна из выдвижной панели;
4. `< 1024`: одна колонка и нижняя навигация «Чат · Очередь · Сроки»; на mobile «Очередь» — самостоятельный раздел, не модалка;
5. проверить минимум 402×874, 834×1194, 1280×720 и 1440+ в обеих темах, включая инспектор документа, тосты, диалог и лоток задач.

Не пытаться лечить это уменьшением масштаба, `min-width` или горизонтальным скроллом: нужен другой сценарий навигации.

### P1 — обязательно до подключения реального API/реальных действий

#### P1-1. Обнаружена high severity зависимость `react-router`

`npm audit --omit=dev --json` сообщает две high-severity записи: `react-router-dom@7.18.1` → `react-router`, advisory `GHSA-qwww-vcr4-c8h2` (CSRF bypass в RSC mode), диапазон, указанный audit: `>=7.12.0 <8.3.0`.

**Исправление.** Не применять вслепую `npm audit fix --force`: предложенный audit downgrade выглядит противоречиво. Сверить advisory и changelog, выбрать подтверждённую безопасную версию, обновить `package.json` и lockfile, затем повторить `npm audit --omit=dev`, build и smoke-тест маршрутов. Даже если текущий SPA не использует RSC/actions, публичный релиз не должен оставлять high CVE в production dependency tree.

#### P1-2. Нет бизнес-валидации редактируемых карточек и защиты границы данных

Формы карточек принимают произвольные строки и позволяют сохранить недействительные юридически значимые данные:

- `renewalNotice.tsx` и `obligationBreach.tsx`: пустой текст уведомления/ответа;
- `evidenceRequest.tsx`: пустой список доказательств, пустые поля «что»/«у кого», неограниченное добавление пунктов и неограниченный `motionText`;
- `paymentDue.tsx`: пустая сумма превращается в `0`, нет верхнего предела/правила точности/проверки валюты;
- date-input проверяет лишь наличие трёх чисел и не проверяет календарную дату/срок относительно бизнес-правил.

Кроме того, `cardsSlice.decide(id, decision, modifiedPayload?: unknown)` принимает `unknown` и без проверки кладёт его в глобальный store. Сейчас это локальный mock, но после подключения API такая граница станет источником некорректных или подменённых решений.

**Исправление.** Ввести схему каждого payload (Zod/Valibot либо строгие type guards) и единый `validateCardDecision(card, payload)`:

1. запускать её перед `confirmEdit` и показывать ошибки у соответствующих полей;
2. проверять длины, обязательность, `trim()`, допустимые символы/диапазоны, количество элементов, finite amount, ISO date и предметные правила сроков;
3. повторять **те же проверки на сервере**. Клиентская проверка — только UX, не защита;
4. не доверять `workspaceId`, `cardId`, `priority`, `sources`, `originThreadId` и payload от браузера: сервер должен брать карточку по id, проверять tenant/роль/статус и разрешённый переход состояния;
5. лимитировать размер сообщения чата и каждой формы до отправки и на API; возвращать понятную ошибку вместо молчаливого обрезания.

#### P1-3. Неверная работа юридических дат в браузере пользователя из другого часового пояса

`src/workspaces/obligations/cards/dateInput.ts` парсит ISO с `+03:00` через `new Date()`, меняет локальные `setFullYear`, затем формирует offset из **часового пояса браузера**. Вне Москвы редактирование меняет instant и/или записывает срок не в юридически установленном `+03:00`.

**Исправление.** В домене разделить date-only срок и timestamp. Для сроков без времени хранить `YYYY-MM-DD` и не пропускать через `Date`; для timestamp хранить timezone IANA/исходный offset и редактировать библиотекой с timezone support. Добавить тесты для `Europe/Moscow`, UTC и timezone с отрицательным offset, включая DST.

#### P1-4. Сбой будущего транспорта агента будет замаскирован как обычная остановка

В `src/core/chat/useAgentStream.ts` обход `for await (transport.send(...))` имеет `try/finally`, но не имеет `catch`. Если реальный SSE/fetch transport бросит исключение (timeout, network error, malformed stream), placeholder-сообщение в `finally` переводится в `complete`, а пользователю не предлагается retry и причины нет.

**Исправление.** Явно ловить исключения, отличать `AbortError` от ошибки транспорта, ставить `MessageStatus = error`, сохранять безопасное понятное сообщение и `retryable`, завершать/ошибочно завершать background task согласованно. Не отображать raw exception, URL, токены или ответ провайдера. Добавить тесты: timeout, HTTP 401/429/5xx, invalid event, abort, размонтирование чата и смена маршрута.

#### P1-5. Модель решений по карточке не защищена от повторов и гонок

`cardsSlice.decide`, `setCardState` и `bulkAccept` меняют состояние локально без проверки допустимого исходного состояния и версии карточки. `useCardDecision` сначала подтверждает решение в store, потом запускает mock-execute. Для реального внешнего действия это создаёт риск двойной подачи/отправки при double-click, retry, двух вкладках или запоздавшем ответе.

**Исправление.** Серверный command endpoint должен требовать `cardId`, допустимое ожидаемое состояние/version (optimistic locking) и idempotency key; разрешать только явную state-machine. Клиент должен отключать все конкурирующие действия, иметь один request controller на карточку и синхронизироваться с серверным результатом, а не считать `done` до подтверждения сервера. Необратимые действия требуют server-side audit trail: кто, когда, что подтвердил и какую версию payload.

## P2 — исправить в этом же цикле до production-quality

### P2-1. Состояние демо не переживает reload, а утренний дайджест может исчезнуть на всю сессию

Store гидратируется заново при reload (`src/main.tsx`), однако `ChatView` запоминает уже выполненный автозапуск в `sessionStorage`. После перезагрузки в той же сессии сообщений нет, но ключ `pravotech:auto-run:thread-today` остаётся: дайджест не будет запущен снова. Все решения по карточкам и сообщения также теряются.

**Исправление.** Для прототипа выбрать и явно описать один вариант: либо не использовать session guard и запускать digest, когда тред пуст, либо сохранять нужный snapshot/версии в storage. Для реального продукта источник правды — API, локально хранить только безопасный кэш; перед рендером проверять пользователя/tenant/версию данных.

### P2-2. Нет автоматических тестов UI/store, dry-run покрывает только happy-path мока

В репозитории нет unit/integration/e2e тестов; `scripts/dry-run-agent.ts` полезен, но не покрывает редактирование карточек, state transitions, маршруты, мобильную раскладку, accessibility и сбои реального транспорта.

**Исправление.** Добавить Vitest + React Testing Library и Playwright. Минимальный набор: валидация payload, timezone, select/queue ordering, разрешённые переходы карточек, transport errors/abort, deep link документа, invalid route/thread, reload digest, keyboard navigation и визуальные/viewport smoke-tests для 402/834/1280/1440. В CI запускать это до deploy.

### P2-3. CI уже деплоит Pages, но не является полноценным quality gate

`.github/workflows/deploy.yml` действительно запускается на каждом `push` в `main`, делает `npm ci`, build и publish. Это хорошая основа, но сейчас не запускает `npm run lint`, `npm run dry-run`, тесты, audit, и не использует отдельный check workflow/branch protection.

**Исправление.**

1. Добавить `ci.yml` для pull request и push: `npm ci` → lint → typecheck/build → dry-run → unit/e2e tests → dependency audit/Dependabot;
2. deploy job оставить только после успешных проверок и только для `main`;
3. включить branch protection: required CI checks, запрет прямого push в `main`, review;
4. закрепить Node через `engines` в `package.json` и использовать одну версию (сейчас workflow использует 22, README говорит Node 18+);
5. хранить только Pages permissions, без secrets в frontend bundle; добавить Dependabot/Renovate.

### P2-4. README и часть внутренних документов расходятся с фактическим кодом

README уже существует и уже описывает запуск и GitHub Pages. Поэтому создавать второй README не нужно — его надо улучшить. `docs/SPEC.md` при этом всё ещё называет React Router 6, тогда как фактически установлена ветка 7; в `HANDOFF.md` указан незавершённый адаптив, но README создаёт впечатление полной готовности.

**Исправление.** Обновить существующий README: назначение и ограничения прототипа (mock/no auth/no persistence), требования Node, команды, architecture map, сценарии демо, запуск production preview, GitHub Pages URL/включение, CI/CD, known limitations, security policy и contribution flow. Синхронизировать SPEC/DOMAIN/DEVLOG с фактическими версиями и принятыми решениями.

### P2-5. Обработка невалидного URL треда не объясняет проблему

При URL треда из другого пространства (`/#/w/obligations/t/thread-lit-a40-position`) код молча открывает экран «О чём поговорим?». Пользователь не понимает, что ссылка неверна, и может создать новый разговор вместо исходного.

**Исправление.** Показать явное `EmptyState`/404 для отсутствующего или чужого `threadId` с действием «К списку диалогов». Аналогично валидировать `tabId` и document/anchor query params; неизвестные значения не должны незаметно менять смысл ссылки.

### P2-6. Производительность и качество сборки

`npm run build` успешен, но Vite предупреждает об одном JS chunk `555.44 kB` (`164 kB gzip`) после minify. `npm run lint` завершился с 15 warnings, главным образом `react(only-export-components)`; в lint также попадают файлы design handoff, которые не являются runtime-кодом.

**Исправление.** Динамически импортировать страницы/тяжёлые поверхности (inspector, KitchenSink, workspace tabs), проверить treeshaking и bundle analyzer. Отделить `design/**` от runtime lint либо настроить исключение. Устранить предупреждения или документированно отключить только точечные, обоснованные случаи. В CI считать новые warnings ошибкой.

### P2-7. Идентификаторы, генерируемые через `Date.now()`, могут столкнуться

Новые треды создаются по `thread-${workspace}-${Date.now()}` в нескольких местах. При очень быстрых двойных действиях/автоматизации в одну миллисекунду возможна перезапись существующей записи.

**Исправление.** Использовать `crypto.randomUUID()` (или серверный id), не конструировать доменный id из времени; добавить тест на быстрый create.

## Безопасность: текущая оценка

### Что сделано хорошо

- В runtime-коде нет `dangerouslySetInnerHTML`, `innerHTML`, `eval` или `new Function`; пользовательский и mock-текст рендерится React-узлами, поэтому типовой DOM XSS сейчас не воспроизводится.
- URL-параметры документа сопоставляются с существующими данными перед открытием; `CSS.escape` используется для selector.
- Нет hard-coded API keys и прямых внешних запросов в браузере.
- Используются безопасные headless primitives Radix для диалогов, tooltip и toast; у icon-only controls в большинстве случаев есть `aria-label`.
- `HashRouter` и относительный Vite `base: './'` подходят для статического GitHub Pages и не требуют server-side rewrite.

### Что обязательно предусмотреть при переходе от mock к продукту

GitHub Pages годится только для публичного статического frontend. Он не обеспечивает аутентификацию, хранение юридических данных, API-авторизацию, security headers или аудит действий. Реальный backend должен быть отдельным доверенным сервисом с:

- SSO/OIDC, RBAC и строгой изоляцией tenant на каждой операции;
- server-side authorization для document/card/thread id, rate limiting, CSRF protection там, где используются cookie;
- schema validation, лимитами размера, content type allowlist и антивирусной проверкой для будущих загрузок документов;
- шифрованием данных, аудитом необратимых действий, журналом доступа к документам и политикой хранения/удаления;
- CSP/HSTS/X-Content-Type-Options/Referrer-Policy на хостинге/API. GitHub Pages не даёт нормально настроить произвольные response headers, поэтому для чувствительного кабинета нужен другой frontend hosting/CDN;
- защитой LLM от prompt injection на стороне orchestration: документы и сообщения — недоверенные данные, не инструкции; tool permissions allowlist, подтверждение пользователя и server-side policy проверка обязательны.

## GitHub Pages, Dockerfile и README — целевое состояние

### GitHub Pages / CI-CD

Основа уже есть: `.github/workflows/deploy.yml` публикует `dist/` на Pages после push в `main`. После выполнения P0/P1 нужно:

1. добавить обязательные CI проверки из P2-3;
2. в GitHub repository settings включить **Settings → Pages → Build and deployment → Source: GitHub Actions**;
3. сделать тестовый PR, затем merge в `main` и проверить опубликованный hash-route, документы, deep links и обе темы;
4. добавить URL опубликованного проекта в README.

### Dockerfile

**Dockerfile не нужен и не используется для GitHub Pages.** Pages публикует уже собранные статические файлы, контейнер там не запускается. Поэтому не надо делать Dockerfile условием Pages deploy.

Если Dockerfile нужен отдельно по требованиям команды — добавить его как опциональный способ локального preview или будущего non-Pages hosting: multi-stage `node:22` build → минимальный `nginx:alpine`, плюс `.dockerignore`, non-root runtime, pinned image digest и проверка image scan. Его запуск/публикация должны быть отдельным workflow и не содержать secrets в image layers.

### README

`README.md` уже есть. Доработать именно его, а не создавать файл заново, по P2-4. В финальной версии обязательно указать: что это прототип, как установить/запустить/build/preview/test, технологический стек, карту архитектуры, демо-сценарии, ограничения (mock agent, нет real auth/API/persistence), порядок CI/CD и URL Pages.
